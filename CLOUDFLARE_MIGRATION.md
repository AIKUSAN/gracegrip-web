# GraceGrip Cloudflare migration runbook

This release builds a Next.js static export for Cloudflare Pages. Only `POST /api/feedback` runs in a Pages Function. The migration was merged after the protected preview, both D1 databases, and the final data check passed. Vercel's Git integration was disconnected before merging so it could not deploy a static export without the Pages Function.

## Release record — 2026-09-23

- Canonical `gracegrip.app` was attached to the Git-integrated Cloudflare Pages project `gracegrip-webapp`. The `www` host uses a Cloudflare Bulk Redirect to the apex, preserving path and query. Pages production branch is `main`; preview URLs are protected by Cloudflare Access.
- The Neon-to-production-D1 import was repeated immediately before and after the domain switch. Both checks found one historical Neon row with the same stable ID and content hash in D1, and no D1-only rows. This count is a cutover snapshot; live feedback may increase it.
- Cloudflare Web Analytics uses manual installation on the homepage with SPA tracking disabled. No analytics token is set for preview builds.
- Retain the last working Vercel production deployment `dpl_B2Npxjc9MwxmREV4MULo1GFtPnk3` (`gracegrip-webapp-a3voo2fj8-aikusans-projects.vercel.app`) and the Neon database through at least **2026-10-23**. Keep D1 as the live feedback store. Before any planned rollback, reconcile D1-only feedback to Neon and verify hashes; repeat after routing settles. The rollback command is in the cutover gate below.
- GitHub `main` requires successful `build` and `Cloudflare Pages` checks from their respective GitHub Apps, with strict up-to-date checks. The obsolete Vercel check was removed when its Git integration was disconnected.

## Local checks

Use Node 24 and run `npm ci`, `npm run lint`, `npm run validate:content`, `node scripts/seo-guard.mjs`, `npm test`, `npm run build`, and `npm run verify:export`. The build output is `out/`. `next dev` serves the UI but does not serve the Pages Function; use `wrangler pages dev out` for a local end-to-end check.

The versioned `wrangler.jsonc` is the deployment source of truth. Its top-level `FEEDBACK_DB` binding points to production D1; `env.preview` points to the separate preview D1. Database IDs are identifiers, not secrets. Run `npx wrangler d1 execute gracegrip-feedback-production --local --file=d1/migrations/0001_user_feedback.sql` before `npx wrangler pages dev out`. Wrangler's local D1 state is separate from either remote database.

## Cloudflare setup and protected preview

1. Confirm the correct Cloudflare account with `npx wrangler whoami`. Create **two** D1 databases named `gracegrip-feedback-preview` and `gracegrip-feedback-production`; record their IDs in the deployment environment. Never put the Neon URL or an API token in Git.
2. Create an empty, temporary Wrangler Direct Upload Pages project named `gracegrip-preview`, with `main` as its production branch. Enable **Settings → General → Enable access policy** before uploading the first preview. Preview URLs are public until this is enabled. This project is only for protected validation; Direct Upload projects cannot later switch to Git integration. Leave the apex and `www` attached to Vercel.
3. Apply `d1/migrations/0001_user_feedback.sql` to each remote D1 database, using `npx wrangler d1 execute <database-name> --remote --file=d1/migrations/0001_user_feedback.sql`. Check table presence and the `id` primary key without selecting feedback text.
4. For the already-created temporary `gracegrip-preview` project, use a local copy of `wrangler.jsonc` with its `name` set to `gracegrip-preview` and deploy with Wrangler's `--config` option. Keep this local copy outside Git. Build with **no analytics token** using `npm run build`, run `npm run verify:export`, then upload `out/` to the Access-protected preview project. Confirm the preview URL requires Cloudflare Access and that `/emergency` opens directly before onboarding. The Git-integrated `gracegrip-webapp` project uses the versioned configuration directly.
5. With `NEON_DATABASE_URL` (or the existing `DATABASE_URL`), `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, and `D1_PREVIEW_DATABASE_ID` available only in the terminal environment, run `node scripts/migrate-neon-feedback.mjs --inspect-source` and `node scripts/migrate-neon-feedback.mjs --target=preview`. The import uses Neon UUIDs and UTC timestamps, `INSERT OR IGNORE`, and verifies every Neon row against D1 using hashes. It prints row counts and column names only. Repeat it to confirm idempotence. By default the verifier also requires the D1 total to equal the Neon count; use `--allow-d1-only` only after deliberately creating preview feedback rows or after production cutover.
6. Exercise the protected preview on desktop and mobile: all six direct URLs, emergency before onboarding, journal encryption and existing backup/QR import, feedback success and error responses with synthetic text, static OG image, sitemap/canonicals, and private-route `noindex`. A service token permitted by the Access policy can run `SEO_HEALTH_BASE_URL=<preview-url> CF_ACCESS_CLIENT_ID=... CF_ACCESS_CLIENT_SECRET=... node scripts/seo-health-check.mjs`. Verify the Web Analytics beacon is absent on every preview route.

## Production and cutover gate

1. Keep the existing Vercel deployment and Neon database available. After preview acceptance, create the final **Git-integrated** Pages project `gracegrip-webapp` from this migration branch. Configure `npm run build` and `out/`; the versioned `wrangler.jsonc` supplies both D1 bindings. Set Node 24 for the build and keep its apex and `www` domains unattached. Initially use the migration branch as its production branch; after the migration is merged, switch its production branch to `main`. Validate its deployed Function binding and Access rules separately from the temporary preview project.
2. Before merging to `main`, stop automatic Vercel production deployments from that branch while retaining the last working Vercel deployment and its live domain. Otherwise the static export would replace Vercel's live feedback route before cutover. Confirm the retained deployment still serves `gracegrip.app`, then merge the accepted migration commit and let the Git-integrated Cloudflare project build `main`.
3. Run `node scripts/migrate-neon-feedback.mjs --target=production --confirm-production` with `D1_PRODUCTION_DATABASE_ID` set. Re-run immediately before routing traffic, then use `--verify-only` for a read-only comparison. A later rerun catches Neon rows created during DNS propagation; pass `--allow-d1-only` once Cloudflare has accepted new feedback so the verifier requires every Neon row to match while reporting D1-only rows.
4. The existing Cloudflare Web Analytics site for `gracegrip.app` is set to **Enable with JS Snippet installation**. Keep Pages' one-click injection and any other automatic injection disabled. Put the existing site's token in `NEXT_PUBLIC_CF_WEB_ANALYTICS_TOKEN` **only for the production build**. The snippet is in `app/page.jsx` with `spa: false`; inspect deployed HTML and navigation to confirm no beacon on inner routes.
5. Validate the Git-integrated Cloudflare deployment before attaching `gracegrip.app`: direct `/emergency` access before onboarding, production `FEEDBACK_DB`, headers, canonical metadata, and expected analytics behavior. Confirm the protected preview, data, and rollback checks before attaching the apex to Pages and routing DNS to it.
6. Configure the Cloudflare `www.gracegrip.app` → `https://gracegrip.app` **Bulk Redirect** with subpath matching, suffix and query preservation, plus a proxied `www` DNS record. Pages `_redirects` cannot express host-based redirects. Confirm a permanent status and exact path/query preservation, then run the live SEO health check and feedback smoke test. Run the manual IndexNow and Search Console workflows only after the domain is verified.
7. Retain the last working Vercel deployment, Neon database, and production D1 for 30 days. For a **planned rollback**, run `node scripts/reconcile-d1-to-neon.mjs --confirm-neon-write` with the production D1 ID and Neon URL, then `--verify-only` before routing traffic back to Vercel. For an **emergency outage**, route the domain back to the retained Vercel deployment immediately, then run reconciliation and verification. The script uses stable IDs, ignores existing identical rows, and fails on conflicting content. In either case, rerun reconciliation and `--verify-only` after DNS propagation to capture late Cloudflare writes; do not consider recovery complete until this final check passes. Do not delete either data source or the old deployment during the 30-day window.

For rollback operations, ensure the Vercel CLI is available (`npm i -g vercel` if missing) and authenticated for the retained project. It provides `vercel env pull`, `vercel deploy`, and `vercel logs`.

Cloudflare Pages' `_headers` rules cover static responses; `functions/api/feedback.js` sets its own no-store and security headers. `public/_routes.json` limits Function invocations to `/api/feedback`. The Pages preview default `noindex` header is a crawler hint, **not** access control; the Access policy is required.

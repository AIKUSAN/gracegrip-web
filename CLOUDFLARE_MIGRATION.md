# GraceGrip Cloudflare migration runbook

This branch builds a Next.js static export for Cloudflare Pages. Only `POST /api/feedback` runs in a Pages Function. Vercel continues to serve `gracegrip.app` until the protected preview, both D1 databases, and final data check are verified. **Do not merge this branch to `main` while Vercel's Git integration can deploy it**: Vercel cannot run the Pages Function, so that would interrupt feedback on the live site.

## Local checks

Use Node 24 and run `npm ci`, `npm run lint`, `npm run validate:content`, `node scripts/seo-guard.mjs`, `npm run test:feedback`, `npm run build`, and `npm run verify:export`. The build output is `out/`. `next dev` serves the UI but does not serve the Pages Function; use `wrangler pages dev out` for a local end-to-end check.

Create a local `wrangler.jsonc` with `CLOUDFLARE_PAGES_PROJECT`, `D1_PRODUCTION_DATABASE_ID`, and `D1_PREVIEW_DATABASE_ID` in the environment, then run `npm run configure:pages`. This file is ignored by Git. Both IDs must be distinct UUIDs. The generated top-level D1 binding is production; `env.preview` overrides it with the preview database. Run `npx wrangler d1 execute gracegrip-feedback-production --local --file=d1/migrations/0001_user_feedback.sql` before `npx wrangler pages dev out`. Wrangler's local D1 state is separate from either remote database.

## Cloudflare setup and protected preview

1. Confirm the correct Cloudflare account with `npx wrangler whoami`. Create **two** D1 databases named `gracegrip-feedback-preview` and `gracegrip-feedback-production`; record their IDs in the deployment environment. Never put the Neon URL or an API token in Git.
2. Create an empty Pages project with Wrangler Direct Upload and set `main` as its production branch. Direct Upload projects cannot later switch to Pages Git integration; a separate Pages project would be needed if Git integration is desired. Enable **Settings → General → Enable access policy** before uploading the first preview. Preview URLs are public until this is enabled. Leave the apex and `www` attached to Vercel.
3. Apply `d1/migrations/0001_user_feedback.sql` to each remote D1 database, using `npx wrangler d1 execute <database-name> --remote --file=d1/migrations/0001_user_feedback.sql`. Check table presence and the `id` primary key without selecting feedback text.
4. Set `CLOUDFLARE_PAGES_PROJECT`, both D1 IDs, and **no analytics token** for the preview build. Run `npm run build:pages`, `npm run verify:export`, then `npx wrangler pages deploy out --branch codex/gracegrip-cloudflare-migration`. Confirm the returned preview URL requires Cloudflare Access and that `/emergency` opens directly before onboarding.
5. With `NEON_DATABASE_URL` (or the existing `DATABASE_URL`), `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, and `D1_PREVIEW_DATABASE_ID` available only in the terminal environment, run `node scripts/migrate-neon-feedback.mjs --inspect-source` and `node scripts/migrate-neon-feedback.mjs --target=preview`. The import uses Neon UUIDs and UTC timestamps, `INSERT OR IGNORE`, and verifies every Neon row against D1 using hashes. It prints row counts and column names only. Repeat it to confirm idempotence.
6. Exercise the protected preview on desktop and mobile: all six direct URLs, emergency before onboarding, journal encryption and existing backup/QR import, feedback success and error responses with synthetic text, static OG image, sitemap/canonicals, and private-route `noindex`. A service token permitted by the Access policy can run `SEO_HEALTH_BASE_URL=<preview-url> CF_ACCESS_CLIENT_ID=... CF_ACCESS_CLIENT_SECRET=... node scripts/seo-health-check.mjs`. Verify the Web Analytics beacon is absent on every preview route.

## Production and cutover gate

1. Keep the existing Vercel deployment and Neon database available. After preview acceptance, run `node scripts/migrate-neon-feedback.mjs --target=production --confirm-production` with `D1_PRODUCTION_DATABASE_ID` set. Re-run immediately before routing traffic, then use `--verify-only` for a read-only comparison. A later rerun catches Neon rows created during DNS propagation; the verifier tolerates new D1-only rows while requiring every Neon row to match.
2. Configure a Cloudflare Web Analytics site for `gracegrip.app`. Disable Pages' one-click injection and any zone-level automatic injection. Put the token in `NEXT_PUBLIC_CF_WEB_ANALYTICS_TOKEN` **only for the production build**. The snippet is in `app/page.jsx` with `spa: false`; inspect deployed HTML and navigation to confirm no beacon on inner routes.
3. Build the accepted commit with `npm run build:pages`, verify it, and deploy the production branch with Wrangler. Confirm its `FEEDBACK_DB` binding points to production D1. Validate the Pages deployment before attaching `gracegrip.app`. Obtain explicit domain-cutover approval after the preview and data checks, then attach the apex to Pages and route DNS to it.
4. Configure the Cloudflare `www.gracegrip.app` → `https://gracegrip.app` **Bulk Redirect** with subpath matching, suffix and query preservation, plus a proxied `www` DNS record. Pages `_redirects` cannot express host-based redirects. Confirm a permanent status and exact path/query preservation, then run the live SEO health check and feedback smoke test. Run the manual IndexNow and Search Console workflows only after the domain is verified.
5. Retain the last working Vercel deployment and Neon database for 30 days. If the new site or feedback path fails, route the domain back to that Vercel deployment, verify the old API, and preserve D1 writes for reconciliation before trying the migration again. Do not delete either rollback source during that window.

The Vercel CLI is not installed in this workspace. For rollback operations, install it with `npm i -g vercel` to use `vercel env pull`, `vercel deploy`, and `vercel logs` against the retained project.

Cloudflare Pages' `_headers` rules cover static responses; `functions/api/feedback.js` sets its own no-store and security headers. `public/_routes.json` limits Function invocations to `/api/feedback`. The Pages preview default `noindex` header is a crawler hint, **not** access control; the Access policy is required.
